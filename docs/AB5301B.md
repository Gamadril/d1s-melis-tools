# AB5301B companion MCU

Two tools target the Bluetrum AB5301B companion MCU of F133-based devices:

* **`mcu_tool`** — offline: decodes and extracts `LTTMcu.bin` update files.
* **`mcu_dump`** — hardware: reads the MCU's own internal flash over UART.
  See [Dumping the MCU flash](#dumping-the-mcu-flash-with-mcu_dump).

Both produce the same decoded files, because the flash image inside an update file is the image that sits on the chip.
`mcu_tool extract` takes either input.

## MCU update extraction with `mcu_tool`

`mcu_tool` decodes and extracts `LTTMcu.bin` updates for the Bluetrum AB5301B companion MCU in F133-based devices.
It reads an update file and writes its contents to a new directory.
It does not flash devices or repack updates.

### Get the binary

Release bundles include `bin/mcu_tool` (`mcu_tool.exe` on Windows).
Run the examples below from that `bin/` directory.

### Extract an update

```bash
./mcu_tool extract path/to/LTTMcu.bin lttmcu-extracted
```

The output directory must not already exist, and its parent directory must exist.
The tool refuses existing files, directories and symlinks at the output path.
Decoding and integrity checks finish before output files are created.

On Windows, use `.\mcu_tool.exe` in place of `./mcu_tool`.

### Options

```bash
# Validate and print the manifest without writing files
./mcu_tool extract LTTMcu.bin lttmcu-check --dry-run

# Extract only the outer package, without decoding its contents
./mcu_tool extract LTTMcu.bin lttmcu-package --outer-only

# Show all extract options
./mcu_tool extract --help
```

`--dry-run` still requires an output argument, and that path must not already exist.
It prints the file information and validation results to the terminal.

`--outer-only` can extract the package from updates whose inner format or boot loader is unsupported.
It checks only the outer wrapper; it does not validate or decode the contents of `package.bin`.
It can be combined with `--dry-run`.

### Output files

| File | Contents |
| --- | --- |
| `original.bin` | Copy of the input update |
| `package.bin` | Update package with the outer wrapper removed and decoded |
| `xcod.bin` | Decoded main executable |
| `xres.bin` | Resource/audio data, when present |
| `boot.bin` | Decoded boot loader |
| `updater.bin`, `ram.bin`, `helper.bin` | Decoded update and startup components |
| `wrapper-header.bin`, `flash-header.bin`, `flash-directory.bin` | Update headers and directory |
| `raw/` | Additional package sections and metadata |
| `manifest.txt` | File information, validation results, hashes and source offsets |

With `--outer-only`, the output contains only `original.bin`, `wrapper-header.bin`, `package.bin` and `manifest.txt`.

### Supported files and errors

Extraction has been verified with several update samples from other systems since I cannot find any update files for HZ-B500.
These use the same command without additional decoding parameters.
Other Bluetrum updates may use unsupported formats or bootloaders.

A write error can leave a partial output directory.
`manifest.txt` is written last, after the other output files have been written.

Successful extraction does not confirm that an update is compatible with your device.
Extracted files are for inspection; the tool does not produce a flashable replacement update.

## Dumping the MCU flash with `mcu_dump`

`mcu_dump` reads the AB5301B's **internal flash** over the chip's mask-ROM UART bootloader and writes the raw image to a file.
It is **read-only**: it never writes or erases flash.
Use it when there is no `LTTMcu.bin` for your device — the dump contains the same `XCOD` code and `XRES` resource regions an update file carries, so it is the way to get at the MCU firmware that drives the UART protocol between the F133 and the MCU.

The datasheet lists the AB5301B's program memory as "internal 8M bit flash" — 1 MiB in the package, with no separate flash chip on the board.
It still behaves like SPI NOR: the ROM and the stub reach it over the chip's internal SPI0 bus, wake it with `0xAB`, read a JEDEC id and drive chip select on GPIOG bit 2.
The id reported by a HZ-B500 class unit is `0xb36014`, whose density byte `0x14` means 1 MiB — the same 8 Mbit.

Protocol details, byte formats and the RAM stub are documented in [CRWN_DUMP_PROTOCOL.md](CRWN_DUMP_PROTOCOL.md).
Verified on a real AB5301B: a 1 MiB dump takes about 46 s at 921600 baud.

### Wiring

The chip's UART download pin is **single-wire half duplex** — one pin is both TX and RX.

* A 3.3 V USB-to-UART adapter, 8N1.
* Tie the adapter's **TX and RX together** through a ~200 Ω resistor, and connect that point to the chip's download pin (`PA7` on AB5301B and has own "GND-DATA-VCC" connector on HZ-B500 board).
* Common ground with the board.

Everything the host sends is echoed back on this wire; `mcu_dump` consumes the echo itself.

### Dump the flash

```bash
./mcu_dump --port /dev/ttyUSB0 ab5301b_flash.bin
```

The tool syncs with the bootloader (resetting the chip if it does not answer), authorizes, switches to 921600 baud, uploads a 412-byte RAM stub that drives the flash over SPI0, and reads the whole chip.
It prints the chip ID, the flash JEDEC and unique IDs, the flash size and the code key (which `mcu_tool` normally recovers on its own — see below):

```text
Chip ID:      BLUECRWN
Load address: 0x00012000
Flash JEDEC:  0xb36014
Flash UID:    0b326730140a13244352432750202220
Flash size:   1048576 bytes
Code key:     0xb5910419
```

On Windows use `.\mcu_dump.exe --port COM3 ...`.
On Linux the serial port usually needs `sudo` or membership in the `dialout` group.

### Options

```bash
# Stay at 115200 baud (about 8x slower; try this if the link is unreliable)
./mcu_dump --port /dev/ttyUSB0 --baud 115200 dump.bin

# Read a region instead of the whole flash
./mcu_dump --port /dev/ttyUSB0 --offset 0x10000 --size 0x8000 region.bin

# Reboot the MCU when the dump finishes
./mcu_dump --port /dev/ttyUSB0 --reboot dump.bin
```

Numbers accept decimal or `0x` hex.
The output path must not already exist; a failed run leaves no file behind, so a retry needs no cleanup.

### Decoding the dump

The raw dump is **scrambled**, and `mcu_tool` decodes it — the same decoder that handles `LTTMcu.bin`, because the dump is the flash image an update file carries:

```bash
./mcu_tool extract ab5301b_flash.bin ab5301b-extracted
```

It recognises a raw dump by its flash header and writes `xcod.bin` (main code), `xres.bin` (resources), `boot.bin`, `flash-header.bin`, `flash-directory.bin`, `raw/` and `manifest.txt` — no `original.bin`, `package.bin` or updater components, since a dump has no update wrapper.

The code key is normally **not needed**: `mcu_tool` recovers the stock key from the validated bootstrap and proves it against every `XCOD` page CRC (`recovered_key` in the manifest, which matches the key `mcu_dump` prints).
Pass the printed key only if a device uses a non-stock user key and the recovery fails:

```bash
./mcu_tool extract ab5301b_flash.bin ab5301b-extracted --code-key 0xb5910419
```

Verified on a real 1 MiB dump: 789/789 `XCOD` and 167/167 `XRES` page CRCs pass, and the decoded `xcod.bin`, `xres.bin` and `boot.bin` are byte-for-byte identical to what [bluetrum-tools](https://github.com/kagaimiq/bluetrum-tools)' `fwunpack.py` produces from the same dump.

### Troubleshooting

| Symptom | Cause |
| --- | --- |
| `no response from the bootloader` | Wrong pin, TX/RX not tied together, no common ground, or the MCU is held in reset by the F133 |
| `unsupported chip` | The part is not an AB53xx ("BLUECRWN"); other Bluetrum families need a different stub |
| `chip never returned data (handler hung?)` | The MCU stopped answering — power-cycle the board and retry |
| Repeated CRC retries, slow dump | Drop to `--baud 115200`, shorten the wire, or check the pull-up resistor |

The RAM stub is uploaded to RAM only and disappears on reset; nothing on the MCU is modified.
